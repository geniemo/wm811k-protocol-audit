## 1. 반도체 도메인 기초

### 1.1 웨이퍼, die, lot

**웨이퍼(wafer)**는 실리콘 원판입니다. 이 원판 위에 회로를 만들고, 다 만든 다음 잘라내면 개별 칩이 됩니다. 자르기 전 원판 위에 격자로 배열된 각 칩 자리를 **die**라고 합니다. 300 mm 웨이퍼 한 장에 die가 수백~수천 개 들어갑니다.

**lot(로트)**은 함께 투입되어 같은 장비, 같은 조건으로 처리되는 웨이퍼 묶음입니다. 관행적으로 25장이 한 lot입니다(FOUP이라는 운반 용기의 표준 수량). 공정은 수백 단계인데, 이 단계들을 lot 단위로 통과시킵니다.

여기서 이 프로젝트 전체를 지배하는 사실이 나옵니다:

> **같은 lot의 웨이퍼는 공정 이력의 대부분을 공유한다.**

같은 챔버, 같은 레시피, 같은 시점의 장비 상태를 겪었습니다. 그래서 어떤 공정 문제가 생기면 그 lot의 여러 웨이퍼에 **비슷한 위치, 비슷한 모양으로** 나타나는 경향이 있습니다.

### 1.2 wafer bin map은 어떻게 만들어지나

회로를 다 만들면 자르기 전에 **웨이퍼 테스트**(EDS, Electrical Die Sorting 또는 wafer sort)를 합니다. 프로브 카드라는 바늘 뭉치를 die에 대고 전기적으로 동작하는지 검사합니다. die 하나하나에 대해 pass/fail이 나옵니다.

이 결과를 웨이퍼의 물리적 좌표에 그대로 얹으면 **wafer bin map**이 됩니다. WM-811K의 각 샘플이 바로 이것이고, 픽셀 값은 세 가지입니다.

| 값 | 의미 |
|---|---|
| `0` | die가 없는 자리 (웨이퍼는 원형, 배열은 사각 격자 → 모서리는 빈칸) |
| `1` | 정상 die (pass) |
| `2` | 불량 die (fail) |

**중요:** 이건 사진이 아니라 **이산 격자**입니다. 각 칸은 "합격/불합격"이라는 범주값이지 밝기 같은 연속값이 아닙니다. 이 사실이 뒤에서 전처리 결정을 좌우합니다(§5.3, §6.4).

### 1.3 왜 결함이 "패턴"으로 나타나나

불량 die가 웨이퍼 위에 무작위로 흩어져 있다면 정보가 별로 없습니다. 그런데 실제로는 **공간적으로 뭉쳐서** 나타나는 경우가 많고, 그 모양이 원인을 시사합니다. 물리적 원인이 공간적으로 작용하기 때문입니다 — 예를 들어 회전 도포는 중심에서 가장자리로 방사형 분포를 만들고, 웨이퍼를 잡는 척은 가장자리에 힘을 가하고, 이물질은 국소적으로 떨어집니다.

WM-811K의 9개 라벨과, 공개 문헌에서 일반적으로 연결하는 원인군은 다음과 같습니다.

| 패턴 | 생김새 | 문헌에서 언급되는 원인군 |
|---|---|---|
| **Center** | 중앙에 뭉침 | 회전 도포/식각의 중심부 불균일, CMP 중앙 편차 |
| **Donut** | 고리 모양 (중심은 정상) | 반경 방향 불균일 — 특정 반경대만 조건 이탈 |
| **Edge-Loc** | 가장자리 일부 국소 | 가장자리 취급, 국소 온도/두께 편차 |
| **Edge-Ring** | 가장자리 전체 띠 | 척/클램프 접촉, 가장자리 배제(edge exclusion) 관련 |
| **Loc** | 중간 어딘가 국소 뭉침 | 파티클(이물), 국소 결함 |
| **Random** | 전면에 흩뿌려짐 | 전면적 오염, 재료 문제 |
| **Scratch** | 가늘고 긴 선 | 기계적 스크래치 — 핸들링, CMP 패드 |
| **Near-full** | 거의 전면 불량 | 심각한 공정 이탈, 장비 사고 |
| **none** | 뚜렷한 패턴 없음 | 랜덤 결함 수준 (대부분의 정상 웨이퍼) |

> **방어선 — 반드시 지킬 것**
>
> 위 매핑은 **공개 문헌에서 일반적으로 언급되는 연결**이지, 특정 팹의 공정 지식이 아닙니다. 실제로는 팹마다, 제품마다, 공정 세대마다 다릅니다. 면접에서 "제가 공정을 압니다"로 넘어가면 첫 꼬리질문에 무너집니다. 안전한 선은 이겁니다:
>
> *"공개 문헌의 패턴–원인 매핑을 근거로, 데이터에서 반증 가능한 형태로 구조화했습니다."*

### 1.4 왜 자동 분류가 필요한가

수율(yield)은 웨이퍼당 정상 die 비율입니다. 수율이 떨어지면 돈이 직접 샙니다. 떨어졌을 때 **어느 공정이 원인인지** 빨리 좁혀야 하는데, 패턴이 단서입니다. Edge-Ring이 갑자기 늘면 가장자리 관련 장비를, Scratch가 늘면 핸들링을 먼저 봅니다.

문제는 양입니다. 하루에 수천 장씩 나오는 맵을 사람이 눈으로 분류하면 느리고 일관성이 없습니다. 그래서 분류기를 만듭니다.

**여기서 이 프로젝트의 출발점이 나옵니다.** 분류기를 만들면 성능을 검증해야 하는데, 그 검증이 배포 상황과 다르면 숫자가 거짓말을 합니다.

## 2. WM-811K 데이터셋 뜯어보기

### 2.1 기본 정보

- 출처: MIR Lab (Roger Jang), 원 논문은 Wu, Jang & Chen, *IEEE TSM* 28(1), 2015
- 총 811,457장, 46,293개 lot에서 수집
- 이 중 **172,950장만 사람이 라벨**을 붙였습니다 (약 21%)
- 파일: `WM811K.pkl` (2.02 GB), 배포 zip은 329 MB

필드는 6개입니다: `waferMap`, `dieSize`, `lotName`, `waferIndex`, `trainTestLabel`, `failureType`.

> **함정 1 — 필드명이 배포본마다 다릅니다.** 원본에 오타가 있어 `trianTestLabel`(i와 a가 뒤바뀜)로 배포된 사본이 돌아다닙니다. 값 형태도 다릅니다 — MIR 공식본은 문자열이고 미라벨은 정수 `0`인데, Kaggle 사본은 `[['Training']]` 같은 중첩 배열로 보고된 사례가 있습니다.
>
> 그래서 이 프로젝트는 컬럼명을 **정규식 `tr.*test.*label`로 런타임에 찾고**, 값은 재귀적으로 언랩하는 함수를 따로 두고 테스트했습니다 (`src/wm811k_audit/data.py`). 컬럼명을 하드코딩했다면 다른 사본에서 바로 깨집니다.

### 2.2 직접 세어본 클래스 분포

| 클래스 | 개수 | 비율 |
|---|---:|---:|
| none | 147,431 | 85.24% |
| Edge-Ring | 9,680 | 5.60% |
| Edge-Loc | 5,189 | 3.00% |
| Center | 4,294 | 2.48% |
| Loc | 3,593 | 2.08% |
| Scratch | 1,193 | 0.69% |
| Random | 866 | 0.50% |
| Donut | 555 | 0.32% |
| Near-full | 149 | 0.09% |

**여기서 즉시 나오는 결론:** 전부 `none`으로 찍는 모델의 정확도가 **85.2%**입니다. 그래서 이 데이터셋에서 accuracy 단독 보고는 의미가 없습니다. Near-full은 149장뿐이라 어떤 지표든 크게 흔들립니다.

### 2.3 맵 크기가 제각각인 이유

라벨된 맵의 고유 shape이 **346가지**입니다. 중앙값은 33×33이고, 범위는 15×3부터 212×204까지입니다.

왜 다를까요? **die 크기가 제품마다 다르기 때문입니다.** 같은 300 mm 웨이퍼라도 큰 칩을 만들면 die가 적게 들어가고(격자가 작음), 작은 칩을 만들면 많이 들어갑니다(격자가 큼). 즉 맵 크기는 곧 제품 종류의 대리 변수입니다.

가장 흔한 shape 4개: 25×27(18,781장), 26×26(14,366장), 30×34(12,400장), 29×26(11,751장).

64×64로 리사이즈할 때 **2.01%만 축소되고 나머지 98%는 확대**됩니다. 이건 나중에 Scratch 성능을 해석할 때 다시 나옵니다.

### 2.4 lot 구조 — 이 프로젝트의 핵심

라벨된 데이터에는 **10,762개 lot**이 있고, lot당 라벨된 웨이퍼 수의 중앙값은 **23장**입니다. 25장 중 23장이라는 건 **라벨링이 lot 단위로 이뤄졌다**는 뜻입니다. 웨이퍼를 랜덤으로 골라 라벨링한 게 아니라, lot을 골라서 그 안을 통째로 라벨링했습니다.

더 중요한 사실:

- 결함 웨이퍼 25,519장 중 **21,141장(83%)**이 "같은 lot에 결함 웨이퍼가 2장 이상"인 lot에 속합니다
- 그런 lot 3,669개 중 **51.5%는 결함 클래스가 한 종류뿐**입니다

즉 **lot 하나가 통째로 "Edge-Ring lot"인 경우가 흔합니다.** 이게 §1.1에서 말한 "같은 lot은 닮는다"의 데이터적 증거이고, lot 누수가 성립할 구조가 실재한다는 확인입니다.

### 2.5 원본 Training/Test 라벨 — 아무도 말해주지 않는 사실

데이터에는 원저자가 넣어둔 `trainTestLabel` 필드가 있습니다. 이 프로젝트에서 **직접 측정해서** 알아낸 것들입니다. 공개 자료 어디에도 이렇게 정리된 곳을 못 찾았습니다.

| 확인한 사실 | 값 |
|---|---|
| Training / Test 규모 | **54,355 / 118,595** — Test가 두 배 이상 큽니다 |
| 두 집합에 걸친 lot | **0개** — 원본 분할은 **lot-disjoint**입니다 |
| lot 번호 범위 | Training 1–46,729 (중앙값 36,921), Test 40,328–47,542 (중앙값 44,422) |
| lot 순서상 구간 수 | **16** (완전히 잘랐다면 2) |
| Test의 none 비율 | **93.3%** (110,701 / 118,595) |
| Training의 none 비율 | **67.6%** (36,730 / 54,355) |

이걸 해석하면:

1. **원저자는 이미 lot 단위로 나눴습니다.** "lot 분할이 필요하다"는 이 프로젝트의 문제의식을 원저자는 2015년에 이미 실천했습니다.
2. **거의 시간순입니다.** 앞 lot이 Training, 뒤 lot이 Test이고 40,328–46,729 구간에서만 섞입니다. 배포 상황(과거로 학습, 미래에 적용)에 가깝습니다.
3. **층화되어 있지 않습니다.** Test는 93%가 none인데 Training은 68%입니다. 클래스 사전확률이 완전히 다릅니다.
4. **학습 데이터가 31%뿐입니다.**

3번과 4번이 나중에 가장 극적인 결과를 만듭니다(§7.4).

### 2.6 중복 맵

라벨된 172,950장 중 **6,502장(3.76%)**이 정확히 동일한 맵을 가진 그룹(3,250개)에 속합니다.

- 그중 6,304장이 `none` — 결함이 하나도 없는 웨이퍼는 전부 `1`로 채워진 동일한 격자가 되므로 당연합니다
- 중복 그룹의 **99.6%가 여러 lot에 걸쳐 있습니다**

마지막 항목이 중요합니다. **lot-disjoint로 나눠도 중복은 남습니다.** lot 분할은 "형제 웨이퍼"를 막지만 "다른 lot의 쌍둥이 맵"은 못 막습니다. 그래서 이 프로젝트는 분할별로 중복률을 따로 진단 지표로 측정합니다.

## 3. 평가 방법론 기초 — 누수와 지표

### 3.1 데이터 누수(data leakage)란

**테스트할 때만 알 수 있어야 할 정보가 학습에 새어 들어간 상태**입니다. 그러면 검증 점수가 실제 일반화 성능보다 높게 나옵니다.

가장 흔한 형태는 **그룹 누수**입니다. 데이터에 자연스러운 그룹이 있는데 그걸 무시하고 개별 샘플 단위로 랜덤 분할할 때 생깁니다.

| 분야 | 그룹 | 무시하면 |
|---|---|---|
| 의료 영상 | 환자 | 같은 환자의 다른 슬라이스가 학습·테스트에 나뉨 |
| 음성 인식 | 화자 | 같은 사람 목소리를 미리 들은 상태 |
| 신약 탐색 | 분자 스캐폴드 | 구조가 거의 같은 분자를 미리 본 상태 |
| **웨이퍼 맵** | **lot** | **형제 웨이퍼를 미리 본 상태** |

해법은 **그룹 분할**입니다. scikit-learn의 `GroupKFold`, `StratifiedGroupKFold`가 이걸 합니다 — 한 그룹의 샘플은 전부 한쪽에만 들어갑니다.

### 3.2 lot 누수를 구체적으로

```
lot 4521 (25장, 전부 Edge-Ring 패턴)

  랜덤 분할:                      lot 그룹 분할:
    20장 → 학습                     25장 전부 → 학습
     5장 → 테스트  ← 누수                (또는 25장 전부 → 테스트)
```

랜덤 분할에서 모델은 "Edge-Ring이라는 개념"을 배우지 않고도 "lot 4521의 생김새"를 외우는 것만으로 테스트를 맞힐 수 있습니다. 시험 문제를 미리 본 셈입니다.

**배포에서 왜 문제냐:** 팹에 분류기를 넣으면 내일 나올 웨이퍼는 **학습 때 존재하지 않던 lot**에서 나옵니다. 형제를 미리 본 상태가 아닙니다. 그래서 랜덤 분할로 잰 점수는 현장 성능보다 높고, "검증에서는 됐는데 현장에서는 안 된다"가 됩니다.

이 프로젝트에서 실제로 측정한 값: 랜덤 분할(`A2`)에서 **테스트 웨이퍼의 98%가 자기 lot의 다른 웨이퍼를 학습셋에 갖고 있었습니다**(`lot_share_rate = 0.98`).

### 3.3 지표 — 왜 accuracy를 혼자 쓰면 안 되나

`none`이 85%인 데이터에서:

| 지표 | 정의 | "전부 none" 모델의 점수 |
|---|---|---|
| **accuracy** | 맞힌 비율 | **0.852** ← 아무것도 못 하는데 높음 |
| **macro-F1** | 클래스별 F1의 단순 평균 | 0.102 |
| **balanced accuracy** | 클래스별 recall의 평균 | 0.111 |

macro-F1과 balanced accuracy는 **모든 클래스를 동등하게** 취급합니다. Near-full 149장과 none 147,431장이 평균에서 같은 무게를 갖습니다. 그래서 희귀 패턴을 못 잡으면 바로 점수가 떨어집니다.

**F1을 다시 정리하면:**
- precision = 그 클래스라고 예측한 것 중 실제로 맞은 비율 (오경보를 벌함)
- recall = 실제 그 클래스인 것 중 잡아낸 비율 (놓침을 벌함)
- F1 = 둘의 조화평균

팹 관점에서 recall은 "결함을 놓치지 않았나", precision은 "멀쩡한 걸 결함이라 하지 않았나"입니다. 둘의 상대적 중요도는 상황마다 다릅니다.

### 3.4 seed 분산 — "그 차이가 노이즈 아닌가"

같은 코드를 seed만 바꿔 돌려도 결과는 조금씩 다릅니다. 가중치 초기화, 배치 순서, GPU 연산 순서 때문입니다.

**어떤 조작의 효과가 이 변동보다 작으면 효과라고 말할 수 없습니다.** 그래서 seed 반복은 선택이 아니라 필수입니다.

이 프로젝트는 seed 3개를 씁니다. 3개로 할 수 있는 것과 없는 것을 구분해야 합니다:

- **할 수 있는 것:** 효과의 크기를 **상한 지음** ("이 효과는 0.01보다 작다")
- **할 수 없는 것:** 작은 효과가 **0이라고 결론** 내기 (검정력이 부족)

이 구분이 §8의 결론 서술을 지배합니다.

## 4. 이 프로젝트의 문제 정의

### 4.1 성능 경쟁은 이미 포화

WM-811K로 98.56%를 보고한 연구도 있습니다. 신입이 모델 성능으로 새로 진입할 여지는 거의 없습니다.

### 4.2 그런데 숫자들이 서로 비교되지 않습니다

공개 저장소·논문 세 개를 직접 확인한 결과입니다.

| 출처 | 분할 | 클래스 | 표본 | 해상도 |
|---|---|---|---|---|
| [arXiv:2605.14255](https://arxiv.org/abs/2605.14255) | lot 그룹 70/15/15 | 9 | 전체 | 64×64 |
| [judahobi/Defect_KAN](https://github.com/judahobi/Defect_KAN) | 층화 랜덤 70/15/15 | 9 | None을 15,000장으로 cap | 224×224 |
| [fr407041/WM-811K...](https://github.com/fr407041/WM-811K_semiconductor_wafer_map_pattern_classified) | 랜덤 60/15/25 | 8 (none 제외) | 결함만 25,519장 | — |

세 선택 모두 합리적입니다. **틀린 게 아니라 서로 다른 질문에 답하고 있습니다.** 문제는 그 결과 숫자를 나란히 놓을 수 없다는 것입니다.

> **표현 규칙 — 절대 지킬 것**
>
> "기존 연구가 틀렸다", "과대평가되어 있다" 같은 서술은 쓰지 않습니다. 오만하게 읽히고, 내 숫자가 낮게 나왔을 때 변명으로 뒤집힙니다. 대신:
>
> *"평가 프로토콜이 성능에 미치는 영향을 측정했고, 제 숫자는 어떤 조건에서 나온 것인지 함께 제시합니다."*

### 4.3 선행 연구 확인 (정직하게)

착수 전에 검색했습니다.

- **있는 것:** lot 그룹 분할 방법론 자체는 arXiv:2605.14255에 이미 있습니다. `lotName` 기반 lot 식별, 결측 0.3% singleton 처리, 64×64 nearest, balanced accuracy + macro-F1까지 명시돼 있습니다. → 방법론이 정당화되어 있으니 "왜 lot으로 묶었나"에 인용할 선례가 있습니다.
- **없는 것:** 그 논문은 lot 분할을 **채택만 하고 랜덤 분할과의 격차는 측정하지 않습니다.** 원문에 "a simple random split would … inflating apparent test performance"라고 주장만 있고 숫자가 없습니다.

**그래서 기여 지점은 "lot 분할을 한 번 하는 것"이 아니라 "격차를 재는 것"입니다.** 개별 선택지가 아니라 축들의 조합 분해입니다.

단, 검색 범위는 웹·arXiv·GitHub였습니다. Google Scholar나 IEEE 전문은 못 봤으므로 **"없다"가 아니라 "못 찾았다"**로 서술해야 합니다.

### 4.4 한 줄 정의

> 모델·학습 절차·seed를 전부 고정한 채 **평가 프로토콜만** 바꿔가며, 보고되는 성능이 얼마나 이동하는지 측정한다. 측정 대상은 모델 성능이 아니라 **프로토콜의 기여도**다.

## 5. 실험 설계와 모든 결정의 근거

### 5.1 요인 설계(factorial design)

한 번에 한 변수만 바꾸는 대신 여러 축을 **조합**으로 돌립니다. 이유는 두 가지입니다.

1. 각 축의 **주효과**(다른 축을 평균 낸 순수 효과)를 뽑을 수 있습니다
2. **상호작용**(축 A의 효과가 축 B 수준에 따라 달라짐)을 볼 수 있습니다 — 한 번에 하나씩 바꾸면 절대 안 보입니다

축 3개(3수준 × 2수준 × 3수준) = **18개 셀**, 각 셀당 seed 3개 = **54 run**.

### 5.2 조작변수 세 축

**축 A — 분할 방식 (3수준 + 보조 1)**

| 코드 | 방식 | 배포 상황과의 관계 |
|---|---|---|
| `A1` | 원본 제공 라벨 그대로 | lot-disjoint + 비층화 + 31/69 |
| `A2` | 랜덤 층화 (`StratifiedKFold`) | lot 혼입 허용 — 누수 있음 |
| `A3` | lot 그룹 (`StratifiedGroupKFold`) | 새 lot에서 검증 — 배포에 가장 가까움 |
| `A4` | lot 번호 순서 (보조) | 유사-시간 분할 |

`A4`는 본 요인설계에 넣지 않고 주 조건에서만 보조로 돌렸습니다. `lotName`이 오름차순이라는 문서 근거는 있지만 그게 **시간순이라는 근거는 없어서** "유사-시간 분할"로만 표기합니다.

**축 B — 클래스 구성 (2수준)**
- `B1`: none 포함 9종
- `B2`: 결함만 8종

**축 C — 클래스당 cap (3수준)**
- `C1`: cap 없음 (전체)
- `C2`: 클래스당 최대 5,000장
- `C3`: 클래스당 최소 클래스 수만큼 (= 119장, 완전 균등)

**적용 순서는 고정입니다: pool → B 필터 → C cap → A 분할 → 학습.** 이 순서를 지켜야 "서브셋을 만든 뒤 나눈다"는 실제 관행을 재현합니다.

### 5.3 통제변수 — 절대 건드리지 않는 것

| 항목 | 값 | 근거 |
|---|---|---|
| 모델 | SmallCNN, 242,345 params | 작을수록 프로토콜 효과가 잘 보임 |
| 옵티마이저 | AdamW lr 1e-3, wd 1e-4 | 관행적 기본값 |
| 학습량 | **8,000 gradient step** | 에폭이 아님 — §6.3 참고 |
| 배치 | 256 | |
| 검증셋 / early stopping | **없음** | §6.5 참고 |
| 증강 | 없음 | 축이 늘면 결론이 흐려짐 |
| 입력 | 64×64, nearest, 3채널 one-hot | §6.4 참고 |
| seed | {0, 1, 2} | |

> **튜닝 금지.** 모델을 조금이라도 손대는 순간 "프로토콜 때문인지 튜닝 때문인지" 구분이 불가능해지고 실험 전체가 무효가 됩니다. 성능이 낮게 나와도 그대로 둡니다.

### 5.4 가장 중요한 설계 결정 — gold 테스트셋

이게 이 프로젝트의 핵심 아이디어입니다.

**문제:** 각 프로토콜이 자기 테스트셋에서 점수를 내면, 축 하나를 바꿀 때 두 가지가 동시에 바뀝니다.

1. 학습 데이터
2. **채점 기준 자체** (테스트셋 구성과 지표 정의)

그러면 숫자 차이의 원인을 분해할 수 없습니다. 구체적으로:

- 9클래스 macro-F1은 none F1(보통 0.99+)이 평균을 끌어올려 8클래스 macro-F1과 **산술적으로** 비교가 안 됩니다
- 균등 소규모 테스트셋에서는 음성 표본이 적어 희귀 클래스 precision이 자동으로 올라갑니다
- 랜덤 vs lot도 "다른 데이터로 학습한 두 모델을 서로 다른 시험지로" 비교하는 셈입니다

**해법:** 실험 시작 전에 **lot-disjoint gold 테스트셋을 한 번 떼어내고, 어떤 셀도 절대 건드리지 않습니다.**

```
전체 라벨 172,950
   │
   ├─ gold  34,615 (20.01%)  ← StratifiedGroupKFold(5, seed=20260825) fold 0
   │                            학습·분할·cap 추출 어디에도 쓰이지 않음
   └─ pool 138,335
         └─ 18개 셀이 전부 이 안에서만 분할·학습
```

그리고 모든 셀을 **두 열로** 보고합니다.

| 열 | 무엇 | 답하는 질문 |
|---|---|---|
| **as-reported** | 그 셀 자신의 테스트셋 점수 | "논문이 보고하는 숫자는 얼마인가" |
| **on-gold** | 같은 가중치를 공통 gold로 평가 | "실제 능력은 얼마인가" |

이렇게 하면:

- 한 모델 안에서 (own − gold) = **같은 가중치로 잰 부풀림**. 가장 깨끗한 누수 측정입니다.
- `A3`는 own ≈ gold가 나와야 하므로 그 자체가 sanity check입니다
- on-gold 열의 변화 = 순수 학습 데이터 효과, (as-reported − on-gold) = 테스트셋/지표 효과

**공통 지표는 결함 8종 평균 F1(`defect_f1`)입니다.** 9클래스 모델의 confusion에서 결함 8종만 뽑으면 8클래스 모델과 정의가 같아집니다. 9클래스 모델이 결함 웨이퍼를 `none`으로 예측하면 그 클래스의 FN이 되고, 어떤 결함 클래스의 FP도 되지 않습니다.

### 5.5 누수 진단 — 성능과 별개로 재는 것

성능 격차만 보면 "왜 그런지"를 모릅니다. 그래서 **모델과 무관하게 분할 자체를 진단**하는 지표를 따로 뒀습니다.

| 지표 | 정의 | 무엇을 말해주나 |
|---|---|---|
| `lot_share_rate` | 테스트 웨이퍼 중 자기 lot이 학습에도 있는 비율 | 누수 기회의 양 |
| `dup_rate` | 테스트 중 학습에 동일 맵이 있는 비율 | 완전 중복 |
| `nn_hamming` | 테스트 각 장에서 가장 가까운 학습 웨이퍼까지의 해밍 거리 | **실질적 근접도** |

마지막 것이 결정적이었습니다(§8.2). 계산은 one-hot 후 GPU 행렬곱으로 `4096 − max(내적)`이고, TF32를 끄고 float32로 정확히 계산합니다.

## 6. 설계에서 어려웠던 지점 6가지

실제로 막혔거나, 처음 안이 틀려서 고친 지점들입니다. **이 절이 면접에서 가장 쓸모 있습니다.**

### 6.1 축 B와 축 C가 독립이 아니었던 문제

**처음 안:** 축 C를 절대 표본 수로 정의 — (1) 전체 172,950, (2) 결함만 25,519, (3) 균등 소규모.

**문제:** `B2`(결함 8종)와 `C2`(결함만 25,519)는 **같은 데이터**입니다.
- `B1 × C2`: none이 0장 → 사실상 8클래스 = `B2 × C2`
- `B2 × C1`: 172,950 중 none을 어디 두나? 버리면 `C2`와 동일

유효 셀이 18개가 아니라 12개가 되고, **B 효과와 C 효과를 분리할 수 없습니다.**

**고친 안:** C를 절대 수가 아니라 **클래스당 cap 규칙**으로 재정의하고 B와 무관하게 같은 규칙을 적용. `C1` cap 없음 / `C2` 5,000 / `C3` 최소 클래스 수. 이제 3×2×3 = 18이 진짜 18개입니다.

> **교훈:** 요인설계에서 축이 서로 독립인지는 **착수 전에** 확인해야 합니다. 돌린 뒤에는 늦습니다.

### 6.2 프로토콜마다 테스트셋이 바뀌는 문제

§5.4에서 다룬 것입니다. 이게 두 번째로 큰 설계 수정이었고, gold 테스트셋 도입으로 해결했습니다.

이 문제를 인식하지 못하면 실험을 다 돌리고도 "이 차이가 학습 데이터 때문인지 시험지 때문인지" 답할 수 없습니다.

### 6.3 에폭이 아니라 step으로 고정한 이유

**에폭 고정의 문제:** 에폭 = 데이터를 한 번 훑는 것. 그런데 셀마다 데이터 크기가 다릅니다.
- `C1`: 110,665장 → 1 에폭 = 432 step
- `C3`: 857장 → 1 에폭 = 3 step

30 에폭으로 고정하면 `C1`은 12,960 step, `C3`는 100 step입니다. **표본 규모 효과와 학습량 효과가 완전히 교락됩니다.**

**그래서 8,000 step 고정.** 동일 연산량이 비교 단위로 가장 단순합니다.

**남는 한계 — 정직하게 적어야 함:** step을 고정하면 이번엔 에폭 수가 비대칭입니다. `C1`은 약 18.5 에폭, `C3`는 약 2,400 에폭입니다. 즉 cap 축 효과에는 "데이터가 적다"와 "같은 데이터를 훨씬 많이 본다"가 섞여 있습니다.

**다행히 반박 근거가 로그에 이미 있습니다:** `C3` 런은 step 3,000쯤에 학습 손실이 1e-3까지 떨어지고, gold defect-F1은 step 1,000부터 이미 정체·하락합니다(0.626 → 0.606). 즉 **덜 학습된 게 아니라 이미 외운 상태**입니다. early stopping을 걸어도 ≈0.63으로, `C1`보다 여전히 0.20 낮습니다.

> **교훈:** 어떤 통제를 선택해도 부작용이 생깁니다. 중요한 건 부작용을 인식하고, 그것이 결론을 뒤집는지 데이터로 확인하고, 문서에 적는 것입니다.

### 6.4 전처리 — nearest-neighbour와 one-hot

**리사이즈:** 픽셀값 0/1/2는 **이산 범주**입니다. bilinear/bicubic 보간을 쓰면 1.37 같은 값이 생기는데, 이건 "정상도 불량도 아닌 die"라는 존재하지 않는 상태입니다. 그래서 nearest-neighbour만 씁니다.

**입력 인코딩:** 같은 논리를 끝까지 밀면, 그 값을 스칼라 한 채널로 넣는 것도 모순입니다. 스칼라는 `0 < 1 < 2`라는 **서열을 강제**합니다 — "die 없음이 정상보다 작고, 정상이 불량보다 작다"는 게 물리적으로 무슨 뜻입니까? 아무 뜻도 없습니다.

그래서 **3채널 one-hot**으로 넣습니다. 세 상태가 대등한 범주가 됩니다.

> 이 두 문장이 면접 꼬리질문 두 개를 막습니다. 그리고 이건 도메인 이해가 전처리 결정으로 이어진 사례입니다 — "왜 그렇게 했나"에 물리적 근거로 답할 수 있습니다.

**남는 한계:** 큰 맵(2.01%)은 축소되면서 1-die 폭 Scratch가 끊길 수 있습니다. Scratch 성능이 낮게 나올 때 대안 설명으로 알고 있어야 합니다.

### 6.5 검증셋을 두지 않은 이유

early stopping을 쓰면 val이 필요한데, **val도 같은 분할 규칙을 따라야 합니다.** 랜덤 val을 쓰면 lot 분할 셀에서 epoch 선택 경로로 누수가 다시 들어옵니다.

가장 단순한 해법은 val을 없애고 step을 고정하는 것입니다. 마지막 가중치로 평가합니다. 1,000 step마다 지표를 로그하지만 **선택에는 쓰지 않습니다**(진단용 학습 곡선).

### 6.6 8클래스와 9클래스를 어떻게 비교할 것인가

`B1` 모델은 9개 중에서 고르고 `B2` 모델은 8개 중에서 고릅니다. macro-F1을 그냥 비교하면 안 됩니다.

**해법:** 공통 지표를 **gold의 결함 8클래스 평균 F1**로 잡습니다. `B1` 모델의 confusion은 8×9(none 예측 열 포함), `B2` 모델은 8×8이지만, 행(정답)이 같은 8개 결함 클래스이므로 평균이 같은 정의가 됩니다.

**주의할 비대칭:** `B1` 모델은 "모르겠으면 none"이라는 기권 선택지가 있고 `B2` 모델은 없습니다. `B2`는 모든 오류가 다른 결함 클래스의 FP가 됩니다. 실제로 gold defect-F1이 0.739 vs 0.740으로 거의 같게 나와서 이 비대칭이 결과를 왜곡하지 않았음이 확인됐지만, **결과를 보기 전에는 알 수 없는 위험**이었습니다.

## 7. 진행 과정과 중간 결과

### 7.1 데이터 확보

MIR 공식 배포본(`http://mirlab.org/dataSet/public/MIR-WM811K.zip`, 329 MB)을 받았습니다. Kaggle 사본과 동일 파일이고 로그인이 필요 없습니다.

파생본(증강·전처리된 Kaggle 사본들)은 **쓰지 않았습니다.** 이유는 두 가지입니다.
1. 주제가 전처리와 분할의 영향 측정인데, 남이 전처리한 걸 받으면 통제변수가 처음부터 오염됩니다
2. 파생본 상당수가 lot 정보를 버려서 **lot 분할 자체가 불가능**합니다

pandas 3.0.5로 8.4초에 로드됐고, 라벨 테이블 변환은 4.6초 걸렸습니다.

### 7.2 EDA에서 나온 예상 밖 사실들

§2.5에 정리한 원본 분할 사실들이 여기서 나왔습니다. **가장 놀라웠던 것 순서:**

1. **원본 분할이 이미 lot-disjoint** (겹치는 lot 0개). "lot 분할이 필요하다"는 문제의식을 원저자가 이미 실천하고 있었습니다.
2. **Test가 Training보다 두 배 이상 큼** (118,595 vs 54,355). 보통 반대라고 가정합니다.
3. **Test의 93%가 none** — 층화가 전혀 안 돼 있습니다.
4. **거의 시간순** — lot 순서상 구간이 16개뿐.

이 시점에서 축 A의 `A1` 수준이 "그냥 또 하나의 랜덤 분할"이 아니라 **완전히 다른 성격의 프로토콜**임이 확정됐습니다.

### 7.3 gold 확정과 스모크

gold를 떼고 검증했습니다.

```
gold 34,615 (20.01%) | pool 138,335 | 합 = 172,950 ✓
lot 교집합: 0 ✓  |  인덱스 분할 완전성: ✓  |  9클래스 모두 존재 ✓
gold 클래스별: [858, 111, 1038, 1936, 718, 173, 238, 30, 29513]
```

Near-full은 gold에 **30장**, Donut은 **111장**뿐입니다. 이 두 클래스의 F1은 단정적으로 서술하면 안 됩니다.

200 step 스모크 런이 6초에 통과, 8,000 step 전체 런(`A3-B1-C1`)이 123초 걸렸습니다. 57런 전체가 약 2시간으로 추정됐습니다.

### 7.4 첫 실제 결과 — 충격

전체 실행의 첫 셀이 `A1-B1-C1`(원본 분할)이었습니다.

```
[1/56] A1-B1-C1-s0: own_macro_f1=0.438  gold_defect_f1=0.781
```

**같은 모델인데 자기 시험지에서는 0.438, 공통 gold에서는 0.781.** 두 열 보고 설계가 실험 시작 30초 만에 값어치를 증명했습니다.

이유는 §2.5에서 이미 봤습니다 — `A1`의 테스트셋은 93%가 none이고 층화되어 있지 않으며, 학습에 31%만 씁니다. 모델이 못하는 게 아니라 **시험지가 다른 것**입니다.

이 한 줄이 이 프로젝트의 논지를 가장 선명하게 보여줍니다: **같은 모델이 0.44로도 0.78로도 읽힙니다.**

### 7.5 랜덤 분할 셀 — 누수는 실재하는데

```
[19/56] A2-B1-C1-s0: own_macro_f1=0.844  gold_defect_f1=0.832  lot_share=0.98
```

`lot_share=0.98` — 테스트 웨이퍼의 98%가 자기 lot의 형제를 학습셋에 갖고 있습니다. **누수 기회는 확실히 존재합니다.**

그런데 `A3`(lot 분할)의 0.836과 비교하면 격차가 **+0.008**뿐입니다. 이 시점에서 "가설이 빗나가고 있다"는 게 보이기 시작했습니다.

### 7.6 cap 축에서 나온 부수적 발견

`A2` 셀들의 `lot_share_rate`를 보니 cap 수준에 따라 크게 달랐습니다.

| 셀 | lot_share | n_train |
|---|---:|---:|
| `A2-B1-C1` | 0.985 | 110,668 |
| `A2-B1-C2` | 0.816 | 18,138 |
| `A2-B1-C3` | 0.202 | 856 |

**cap이 누수량 자체를 바꿉니다.** 클래스당 119장만 뽑으면 같은 lot의 형제가 함께 뽑힐 확률이 낮아지기 때문입니다. 축들이 독립적으로 작동하지 않는다는 실증이고, 요인설계를 했기 때문에만 보이는 결과입니다.

*(참고: 여기서 제 검증 코드가 한 번 잘못 실패했습니다. "랜덤 분할은 lot_share > 0.5여야 한다"는 임계값을 넣었는데 `C3`가 0.20이라 걸렸습니다. 코드가 아니라 **제 가정이 틀린 것**이었고, 임계값을 고쳤습니다.)*

### 7.7 전체 결과와 두 번째 반전

57런이 끝나고 분석을 돌렸습니다.

| 축 | 지표 | 범위(max−min) |
|---|---|---:|
| cap | gold defect-F1 | **0.211** |
| split | gold defect-F1 | 0.047 |
| classes | gold defect-F1 | 0.001 |

**표본 선택이 분할 방식보다 4.5배 큰 교란 요인입니다.** 예상과 순서가 뒤바뀌었습니다.

그리고 confusion matrix에서 두 번째 반전이 나왔습니다. 계획 단계에서 저는 "Edge-Loc과 Scratch를 혼동할 것"이라고 적어뒀습니다. 둘 다 가장자리 근처 길쭉한 클러스터라 형태가 비슷하니까요.

**실제로는 전혀 달랐습니다.**

| 정답 | recall % | `none`으로 샌 비율 |
|---|---:|---:|
| Edge-Ring | 96.4 | 2.2 |
| Random | 94.6 | 1.7 |
| Near-full | 93.3 | 0.0 |
| Center | 82.9 | 12.4 |
| Donut | 71.5 | 0.3 |
| Edge-Loc | 72.0 | **21.5** |
| Loc | 59.4 | **25.5** |
| Scratch | 55.6 | **31.5** |
| none | 99.5 | — |

지배적인 실패는 **결함을 `none`으로 놓치는 것**입니다. Edge-Loc↔Scratch 혼동은 2.8%로 미미합니다.

**팹 관점에서 전혀 다른 문제입니다.** 제가 예상한 건 "잘못된 모듈로 대응이 간다"(오분류)였는데, 실제는 "결함을 아예 못 잡는다"(미검출)입니다. 대응이 달라집니다 — 전자는 클래스 분리를 개선해야 하고, 후자는 결함/정상 판별 임계를 조정하거나 소수 클래스 가중을 봐야 합니다.

### 7.8 왜 lot 누수가 작았나 — 메커니즘 확인

성능 격차가 작다는 것만으로는 "왜"를 모릅니다. `nn_hamming` 진단이 답을 줬습니다.

```
테스트 웨이퍼 → 가장 가까운 학습 웨이퍼까지의 해밍 거리 (64×64 = 4,096칸 중)
  랜덤 분할  : 중앙값 361
  lot 그룹 분할: 중앙값 355
```

**거의 같습니다.** lot을 섞긴 섞는데, 어차피 다른 lot에도 비슷하게 생긴 웨이퍼가 많아서 **추가로 샐 것이 별로 없었습니다.**

이게 "성능 차이가 작다"는 관찰에 물리적 설명을 붙여줍니다. 성능 숫자만 보고했다면 "왜 작냐"에 답할 수 없었을 것입니다.

### 7.9 모델을 키워도 같은가 — ResNet-18 검증

"lot 누수가 안 보이는 건 모델이 작아서 아니냐"는 반박이 예상됐습니다. 그래서 파라미터 **46배**(242,345 → 11,173,449)인 ResNet-18을 **완전히 동일한 하이퍼파라미터**로 돌렸습니다(튜닝 없음).

| 격차 | 지표 | SmallCNN | ResNet-18 |
|---|---|---:|---:|
| 분할 (랜덤 − lot) | as-reported | +0.007 | **+0.007** |
| 분할 (랜덤 − lot) | gold | −0.003 | **−0.000** |
| 표본 cap (119장 − 전체) | as-reported | −0.186 | −0.211 |
| 표본 cap (119장 − 전체) | gold | −0.225 | −0.242 |

절대 성능은 ResNet-18이 모든 셀에서 높습니다(gold 기준 +0.04~0.06). 하지만 **분할 격차는 소수점 셋째 자리까지 동일**하고, cap 격차는 오히려 더 커집니다.

**결론이 모델 용량의 인공물이 아님이 확인됐습니다.**

### 7.10 마지막에 발견한 버그 — 숫자가 안 맞는 걸 눈치채기

ResNet 런이 끝난 뒤 confusion 표를 다시 보다가 `gold support`가 이상했습니다. Center가 5,148인데 gold의 Center는 858장이니 3 seed면 2,574여야 합니다. **5,148 = 858 × 6**이었습니다.

원인: 표를 만드는 코드가 `glob("A3-B1-C1-s*")`로 디렉토리를 찾는데, 이 패턴이 `A3-B1-C1-s0-resnet18`까지 잡았습니다. ResNet 런이 생긴 순간부터 **표와 그림이 두 모델의 예측을 조용히 섞고 있었습니다.**

`-s<숫자>`로 끝나는 이름만 매칭하도록 고치고 회귀 테스트를 추가했습니다.

> **교훈:** 지표 숫자가 아니라 **support 같은 부수 정보가 이상하다**는 데서 버그가 잡혔습니다. 표를 만들 때 "몇 개를 세었는가"를 함께 출력하는 것이 이래서 중요합니다. 그리고 glob 패턴은 나중에 추가될 이름까지 생각해야 합니다.

## 8. 최종 결과와 해석

### 8.1 대표 숫자

> **가장 엄격한 조건**(`A3-B1-C1`: lot 그룹 분할 + 9클래스 + cap 없음)에서
> **gold 9클래스 macro-F1 = 0.839 ± 0.005** (3 seed)

배포 상황에 가장 가깝기 때문에 이걸 대표값으로 씁니다.

**말하는 순서를 지킵니다: 숫자 먼저, 조건 나중.**
- 좋음: "가장 엄격한 조건에서 macro-F1 0.839입니다. 같은 모델로 랜덤 분할하면 0.843까지 올라갑니다."
- 나쁨: "조건에 따라 다른데요, 사실 이 데이터셋은..." → 방어적으로 들립니다

### 8.2 세 축의 효과

| 조작 | as-reported | gold | 판정 |
|---|---:|---:|---|
| **분할** (랜덤 − lot) | +0.007 | −0.003 | seed 노이즈 이내 |
| **클래스** (8종 − 9종) | +0.034 | +0.001 | gold 기준 거의 0 |
| **표본 cap** (119장 − 전체) | −0.186 | −0.225 | **압도적 1위** |
| **원본 분할** (`A1` own vs gold 9클래스) | 0.440 | 0.659 | 시험지 차이 |

**분할 축을 정확히 서술하는 법.** 이게 통계적으로 가장 조심해야 하는 부분입니다.

- seed별 격차: +0.0105, +0.0052, +0.0051 → **부호는 3/3 일관**
- 페어드 평균 0.0070, sd 0.0031
- 비교 대상 두 셀의 seed std: 0.0039(`A2`), 0.0043(`A3`)
- 판정 기준(gap < 2×std): 0.0070 < 0.0086 → **구분 불가**

**따라서 올바른 서술은 "효과가 없다"가 아니라 "n=3에서 효과를 ≤0.01로 상한 지을 수 있다"입니다.** 부호가 일관되므로 0이라고 단정할 근거는 없습니다.

*(참고: 초기에 저는 전체 셀 평균 seed std인 0.0112를 기준으로 썼는데, 이 값은 노이즈가 큰 `C3` 셀들에 좌우된 것이라 **비교 대상과 무관한 잣대**였습니다. 최종 리뷰에서 지적받아 셀별 std로 고쳤습니다.)*

### 8.3 시나리오별 해석 — 미리 정해뒀던 것

실험 전에 어떤 결과가 나와도 결론이 있도록 정해뒀습니다. 이게 설계의 일부입니다.

| 시나리오 | 실제 | 해석 |
|---|---|---|
| lot 분할에서 뚜렷한 하락 | ✗ | — |
| 하락이 미미 | **✓** | 이 데이터셋에서는 lot 상관이 약함 → 보고된 성능 차이는 실제 모델 차이일 가능성이 높음 |
| 표본 규모 영향이 분할보다 큼 | **✓** | 성능 비교 시 **가장 먼저 확인할 축을 특정**한 것 |
| 축 간 상호작용 | 소폭 (RMS 0.030) | `A1`/`A4` 셀에서 테스트셋이 축과 함께 변하는 데서 발생 |

**밋밋한 결과를 두려워하지 않는다** — 답을 정해놓고 그쪽으로 가지 않았다는 것이 오히려 신뢰 신호입니다.

### 8.4 실무적 함의

이 결과를 실무 언어로 옮기면:

> WM-811K에서 논문 간 성능 숫자를 비교할 때 **가장 먼저 확인해야 할 것은 분할 방식이 아니라 "몇 장으로, 어떤 클래스 구성으로 학습·평가했는가"**입니다.

그리고 배포 관점에서는:

> lot 분할도 배포 조건의 상한이 아닙니다. 신제품 투입이나 레이아웃 변경은 lot 분할로도 잡히지 않습니다. 이 데이터셋에서 lot 상관이 약했다는 것이 실제 라인에서 분포 이동이 없다는 뜻은 아닙니다.

### 8.5 한계 (전부 적어둘 것)

1. **lot 분할 ≠ 배포 조건의 상한.** 신제품·레이아웃 변화는 못 잡습니다.
2. **step 고정의 에폭 비대칭** — §6.3. 로그로 반박했지만 명시해야 합니다.
3. **n=3** — 효과를 상한 지을 뿐 작은 효과를 해소하지 못합니다.
4. **희귀 클래스** — Donut gold 111장, Near-full gold 30장. 클래스별 F1을 단정하지 않습니다.
5. **패턴–원인 매핑은 문헌 일반론**이지 팹 지식이 아닙니다.
6. **선행 연구 검색 범위**는 웹·arXiv·GitHub. "없다"가 아니라 "확인 못 했다".
7. **아키텍처 불변성이 아님** — 두 모델은 같은 예산·같은 해상도를 씁니다. 확인한 건 파라미터 수에 대한 불변성입니다.

## 9. 구현에서 배울 점

### 9.1 재개 가능한 실험 설계

57런이 2시간, ResNet 9런은 훨씬 더 걸립니다. 중간에 끊기면 처음부터는 재앙입니다.

```python
done = completed_run_ids(csv_path)          # results.csv를 읽어 이미 끝난 run_id 수집
todo = [(c, s) for c in cells for s in seeds
        if run_id_for(c, s, model) not in done]
```

**run 단위로 CSV에 append**하므로, 죽어도 잃는 건 진행 중이던 한 런뿐입니다. 실제로 학습을 중단했다가 재개했을 때 8/9이 그대로 보존됐습니다.

### 9.2 결정론

```python
random.seed(seed); np.random.seed(seed); torch.manual_seed(seed)
torch.cuda.manual_seed_all(seed)
torch.backends.cudnn.benchmark = False
torch.backends.cudnn.deterministic = True
```

`benchmark=True`는 입력 크기에 따라 알고리즘을 자동 선택하는데, 그러면 실행마다 결과가 미세하게 달라집니다.

**단, 이건 "분포적 재현성"이지 비트 단위 일치가 아닙니다.** `torch.use_deterministic_algorithms(True)`는 켜지 않았습니다(성능 대가가 큼). 문서에 그렇게 적어야 합니다.

### 9.3 진단을 성능과 분리

`lot_share_rate`, `dup_rate`, `nn_hamming`은 모델을 전혀 쓰지 않습니다. **분할만으로 계산됩니다.**

덕분에 §7.8처럼 "성능 차이가 왜 작은지"를 설명할 수 있었습니다. 성능 숫자만 모았다면 관찰은 있고 설명은 없었을 것입니다.

### 9.4 검증을 코드에 박아두기

```python
if not set(lots[pool]).isdisjoint(set(lots[gold])):
    raise RuntimeError("gold and pool share lots")
if set(pool) | set(gold) != set(range(len(meta))):
    raise RuntimeError("gold and pool do not partition the labeled set")
```

gold 격리는 이 실험의 **모든 결론이 의존하는 단 하나의 불변식**입니다. 그래서 매 실행 시작 시 실제 데이터에 대해 검사합니다. 문서에만 적어두면 나중에 조용히 깨집니다.

*(초기 구현은 개수만 비교(`len(pool)+len(gold)==len(meta)`)했는데, 한 인덱스가 양쪽에 들어가고 다른 하나가 빠져도 통과합니다. 리뷰에서 지적받아 인덱스 단위로 고쳤습니다.)*

### 9.5 TDD와 합성 fixture

테스트 72개 전부 **합성 데이터**로 돕니다. 708 MB 실데이터를 읽지 않으므로 30초면 끝납니다.

fixture(`tests/conftest.py`)에는 실제 데이터의 함정을 일부러 심어뒀습니다 — 다양한 맵 크기, lotName 결측, 정수 0 미라벨 행, 중첩 배열 라벨, **같은 lot 내 중복 1쌍과 lot 간 중복 1쌍**.

진단 지표 테스트는 결과를 하드코딩하지 않고 **brute force로 재계산해서 대조**합니다.

```python
exp_dup = np.mean([h in set(train.raw_hash) for h in test.raw_hash])
assert d["dup_rate"] == pytest.approx(exp_dup)
```

이 프로젝트의 산출물이 곧 이 숫자들이므로, 회귀 방지가 실질적으로 중요합니다.

### 9.6 문서의 숫자를 추적 가능하게

초기에는 클래스별 recall이 `results/runs/*/metrics.json`에만 있었는데, 이 디렉토리는 gitignore 대상입니다. **저장소를 clone한 사람은 README의 숫자를 확인할 방법이 없었습니다.**

`results/tables/confusion_gold_A3-B1-C1.md`를 생성해 커밋하도록 고쳤습니다. **문서의 모든 숫자는 커밋된 파일에서 재확인 가능해야 합니다.**

## 10. 질문에 답하기

### 90초 요약

> 웨이퍼 맵 결함 분류는 공개 데이터에서 성능이 이미 포화된 문제인데, 보고된 숫자들이 서로 비교가 안 되는 상태였습니다. 분할 방식, 클래스 구성, 표본 규모가 논문마다 다릅니다.
>
> 그래서 모델과 seed를 고정하고 평가 조건만 조합으로 바꿔 18개 셀 × 3 seed를 돌렸습니다. 프로토콜마다 시험지가 달라지는 문제를 없애려고, lot 단위로 20%를 미리 떼어 어떤 학습에도 쓰지 않는 공통 테스트셋을 만들고 모든 조건을 두 열로 보고했습니다.
>
> 가장 크게 작용한 건 **표본 선택**이었습니다. 클래스당 119장으로 균등하게 줄이면 공통 테스트셋 기준 0.225 떨어집니다. 반면 lot을 섞는 랜덤 분할의 효과는 0.007로, seed 노이즈 이내였습니다. 랜덤 분할에서 테스트 웨이퍼의 98%가 같은 lot 형제를 학습에 갖고 있었는데도요. 이유도 확인했습니다 — 최근접 학습 웨이퍼까지의 거리 분포가 두 분할에서 거의 같았습니다. 파라미터 46배인 ResNet-18에서도 같은 결과였습니다.
>
> 가장 엄격한 조건에서 macro-F1은 0.839입니다. 다만 실제 라인에서 어느 조건이 배포 상황에 가까운지는 제가 판단할 수 없는 영역이라, 그 부분은 여쭤보고 싶습니다.

마지막 문단이 이 프로젝트의 목적입니다. **모르는 것을 정확히 모른다고 말할 수 있는 위치까지 가는 것.**

### 예상 질문

**"다들 하는 분류 성능 경쟁은 왜 안 했나"**
→ 논문마다 분할, 클래스 수, 표본 규모가 달라 제 숫자를 어디에 놓을지 알 수 없었습니다. 그래서 축을 먼저 고정했습니다. 회피가 아니라 순서 문제입니다.

**"왜 lot으로 묶었나"**
→ 배포 시점에는 학습에 없던 lot이 들어오는데, 랜덤 분할은 같은 lot의 형제 웨이퍼를 학습과 테스트가 공유하게 만듭니다. 실제로 이 데이터에서 랜덤 분할 시 테스트의 98%가 그런 상태였습니다.

**"그 차이가 노이즈 아닌가"**
→ 맞습니다, 분할 축은 그렇습니다. seed 3개로 확인했고 비교 대상 셀의 표준편차가 0.004인데 격차가 0.007이라 2배 기준 안에 들어옵니다. 다만 부호는 3 seed 모두 같은 방향이어서, "효과가 없다"가 아니라 "0.01 이하로 상한 지을 수 있다"가 정확한 서술입니다.

**"모델이 커지면 달라지지 않나"**
→ 파라미터 46배인 ResNet-18을 동일 하이퍼파라미터로 돌렸습니다. 절대 성능은 0.04~0.06 올랐지만 분할 격차는 +0.007로 동일했습니다.

**"실제 라인 데이터는 다를 텐데"**
→ 판단할 수 없는 영역입니다. lot 분할도 배포 조건의 상한은 아니어서, 신제품이나 레이아웃 변경은 이 실험으로 잡히지 않습니다.

**"이 결과로 뭘 할 수 있나"**
→ WM-811K 결과를 비교할 때 먼저 확인해야 할 축을 특정한 것입니다. 분할 방식보다 표본 구성을 먼저 봐야 합니다. 그리고 후속 개선(준지도 학습 등)을 주장하려면 프로토콜이 고정돼 있어야 하는데, 그 기반이 만들어졌습니다.

## 11. 더 공부할 것

### 이 프로젝트에서 이어지는 것

**확장 1 — 미라벨 데이터 활용.** 811,457장 중 약 79%가 라벨이 없습니다. 준지도 학습(pseudo-labeling, consistency regularization, SimCLR 계열)으로 이를 활용했을 때의 개선을 **고정된 프로토콜 위에서** 측정합니다. 프로토콜이 고정돼야 개선을 주장할 수 있다는 게 이 프로젝트의 전제입니다.

**확장 2 — 원인 진단.** 분류기 출력 + 공간 통계(반경·각도 분포, 클러스터 형상, 결함 밀도) + lot 내 반복성 지표를 융합해 원인 가설을 세우고, 규칙 기반 검증 노드가 반증 가능한 형태로 검정하는 구조. 예: "Edge-Ring이면 같은 lot의 다른 웨이퍼에도 edge 편향이 나타나야 한다"를 조건으로 걸고 실제 lot 데이터로 확인.

최대 난점은 **원인 가설에 정답이 없다는 것**입니다. 공개 문헌의 패턴–원인 매핑을 채점 기준으로 삼고 반증 통과율을 별도 지표로 두는 설계가 필요합니다.

### 방법론 쪽

- **그룹 분할의 다른 사례** — 의료 영상의 patient-level split, 화학의 scaffold split. 같은 문제가 분야마다 어떻게 다뤄지는지 보면 논리가 단단해집니다.
- **불균형 학습** — focal loss, class-balanced loss, 재샘플링. 이 프로젝트는 의도적으로 안 썼지만(축이 늘어나므로), 다음 단계에서는 필요합니다.
- **분포 이동(distribution shift)** — covariate shift, label shift, domain adaptation. "lot 분할도 상한이 아니다"의 이론적 배경입니다.
- **통계적 검정력** — n=3의 한계를 정량적으로 이해하려면. paired t-test, 효과 크기, 신뢰구간.

### 도메인 쪽

- 웨이퍼 테스트(EDS) 흐름과 bin 코드 체계
- 수율 분석 일반 — systematic vs random yield loss
- SPC(통계적 공정 관리)와 이상 탐지가 팹에서 실제로 쓰이는 방식
- 공정 단계별 대표적 결함 모드

**단, 도메인 공부는 "문헌에서 이렇게 설명한다"까지가 안전선입니다.** 실제 팹의 공정 조건은 회사 자산이고, 외부에서 알 수 없습니다.
